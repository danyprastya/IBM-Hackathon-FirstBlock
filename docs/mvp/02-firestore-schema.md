# 02 — Firestore Schema

## Collection layout

All pipeline data is scoped under the user's uid. Each stage's versions live in its own subcollection — never as arrays on the parent. This enables partial writes, per-section listeners, and trivial version history.

```
users/{uid}                                  ← top-level user doc, holds onboarding profile
  └─ problems/{problemId}                    ← rawInput (verbatim founder text), createdAt
       └─ researches/{researchId}            ← brief, status, founderDecision, compactedContext
            └─ solutionCollections/{scId}    ← solutionCount, status, compactedContext
                 └─ solutions/{solId}        ← direction, brief, status, founderDecision
                      ├─ mvps/{mvpId}                ← scopeIn[], scopeOut[], founderConfirmed
                      ├─ successMetrics/{smId}       ← metrics{adoption,value,business}, founderConfirmed
                      └─ prds/{prdId}                ← fullPrd, mvpRef, metricsRef
                           └─ phases/{phaseId}       ← version, order, content, status
```

Conventions:
- Document IDs are auto-generated by Firestore (`adminDb.collection(...).doc()` returns a fresh id).
- `createdAt` is `FieldValue.serverTimestamp()` on writes, `Date` on reads.
- All version-tracking is convention-based — sort the subcollection by `createdAt` and treat the latest as "active." There is no `activeXxxId` pointer field on parent docs.
- `cleanedStatement` exists on `ProblemDocument` for backwards compatibility but is **not populated by AI**. Treat as deprecated; planned removal in `docs/execute/01-purge-cleaned-statement.md`.

## Out-of-pipeline collections

These exist in the deployed app but are not part of the agent pipeline. Don't extend them as part of MVP work:

- `messages/` — chat assistant history
- `stickies/` — sticky notes
- `users/{uid}.rateLimit` — per-user request counter

## TypeScript document interfaces

`lib/firebase/collections.ts` is the source of truth. Types live there alongside the constants:


## Path helpers

`lib/firebase/collections.ts` exports a `PATHS` object — single source of truth, **use it everywhere**:

```ts
PATHS.user(uid)
PATHS.problems(uid)
PATHS.problem(uid, pid)
PATHS.researches(uid, pid)
PATHS.research(uid, pid, rid)
PATHS.solutionCollections(uid, pid, rid)
PATHS.solutionCollection(uid, pid, rid, scId)
PATHS.solutions(uid, pid, rid, scId)
PATHS.solution(uid, pid, rid, scId, solId)
PATHS.mvps(uid, pid, rid, scId, solId)
PATHS.mvp(uid, pid, rid, scId, solId, mvpId)
PATHS.successMetrics(uid, pid, rid, scId, solId)
PATHS.successMetric(uid, pid, rid, scId, solId, smId)
PATHS.prds(uid, pid, rid, scId, solId)

PATHS.phases(uid, pid, rid, scId, solId, prdId)
PATHS.phase(uid, pid, rid, scId, solId, prdId, phaseId)
```

The constants `COLLECTIONS` (`USERS`, `MESSAGES`, `STICKIES`) and `SUBCOLLECTIONS` (`PROBLEMS`, `RESEARCHES`, `SOLUTION_COLLECTIONS`, `SOLUTIONS`, `MVPS`, `SUCCESS_METRICS`, `PRDS`, `PHASES`) sit alongside as the raw segment names.

## Security rules

`firestore.rules` (already deployed) — owner-only access per collection. Pipeline subcollections inherit the parent's user-scoped match. Reference shape:

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid}/{document=**} {
      allow read, write: if request.auth != null && request.auth.uid == uid;
    }
    // out-of-pipeline collections (messages, stickies) have their own rules — see firestore.rules
  }
}
```

The agent's API routes use the Admin SDK, which bypasses rules — so server-side writes work regardless. Rules only constrain client-side access.

## Indexes

`firestore.indexes.json` declares composite indexes for the chat + sticky queries. Pipeline subcollections don't need composite indexes for MVP because every query scans a single subcollection scoped by parent path. Add an index here if a future query orders by `createdAt` and filters by another field.

## Write patterns

**Server-side writes (API routes — the source of truth for agent output):**

```ts
import { adminDb } from "@/lib/firebase/admin";
import { PATHS } from "@/lib/firebase/collections";
import { FieldValue } from "firebase-admin/firestore";

// Create a research doc with status=running
const researchRef = adminDb.collection(PATHS.researches(uid, problemId)).doc();
await researchRef.set({
  id: researchRef.id,
  createdAt: FieldValue.serverTimestamp(),
  status: "running",
  brief: { /* placeholder */ },
  founderDecision: null,
  compactedContext: "",
});

// ... agent runs ...

await researchRef.update({ status: "complete", brief });
```

**Client-side writes (gate decisions, founder confirmations, problem submission):**

Either go through API routes (preferred — gives you sanitization + auth) or write directly via the client SDK using the same path helpers. The route layer is what writes agent output; the client writes direct user actions.

## Verifying

After wiring the schema:
1. Sign in.
2. Hit `POST /api/agents/problems` (or use the workspace UI once `docs/execute/05-agent-ui.md` lands) with `{ rawInput: "test problem" }`.
3. Check Firestore Console → you should see `users/{your-uid}/problems/{id}` with `rawInput: "test problem"` and `cleanedStatement: ""`.
4. Try as another user (incognito + different account) — Firestore rules simulator should deny reading the first user's data.
